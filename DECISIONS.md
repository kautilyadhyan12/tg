- (THE DESIGN CORRECTION THAT MAKES THE CARD WORK) The plan originally released the key on failure so a retry could proceed. Instead the failed attempt's thread id is remembered (`coach:idem:t:*`) and the retry CONTINUES IN IT. `service.chat` gained one optional `onThreadOpened` hook, fired the instant the row commits, so the guard learns the id even when the request later throws — no error-class surgery and it covers every failure type, not just `CoachError`.
- (KEY LAYOUT, and why three keys) `coach:idem:r:{userId}:{sha256(key)}` stores the completed answer (10 min); `coach:idem:c:*` is the atomic in-flight claim (**120 s only**); `coach:idem:t:*` holds a failed attempt's thread. The record is read BEFORE the claim, so a process that died mid-request can never shadow a genuinely stored answer, and the short claim TTL means such a crash strands the key for two minutes rather than the full replay window. `incrWithTtl` is the atomic primitive (real Redis = a Lua INCR+EXPIRE script; the in-memory impl is synchronous JS). All keys are userId-scoped (R3.2) — a stranger's key can never resolve to another person's answer or thread, pinned by a cross-user route test.
- (ALL BOOKKEEPING IN ONE `onSend` HOOK, deliberately) A request can be turned away by a LATER preHandler — the cap, or `requireQuota`'s 429 — without the handler ever running, and that claim still has to be released or an honest retry meets a 409 instead of the real reason it failed. A hook is the only place that sees every outcome. Success stores the answer and drops the orphan-thread key; any other status releases the claim and, if a thread was opened, remembers it.
- (FAIL-OPEN, per the coach doctrine) Redis down → `incrWithTtl` returns null → the question proceeds WITHOUT dedupe and the skip is logged (`coach.idempotency_skipped_redis_down`). Coach quota already fails open (quotas/service.ts `FAIL_OPEN.coach`); refusing a legitimate first question because Redis blipped is worse than a rare duplicate. Never silent — the log line is the signal.
- (an unreadable stored record: THIS attempt refuses, the record is DELETED) Re-running immediately would duplicate, which is the one thing the file exists to prevent — so the attempt 409s. But the record is dropped first, so the NEXT attempt under the same key re-runs cleanly. **AMENDED at T3 round 2 (R11.3):** as first written this line justified the 409 with "the user can always send under a fresh key, so nothing is truly stranded" — false for the client this card is built for, which retries with the SAME key by design, and the code was changed at round 1 (F9) to stop relying on it. The rationale is corrected here rather than left describing a design that no longer exists.
- (NOT the auth module's `createDualRateLimit`, and why) That limiter also counts a per-IP dimension, which on a gym's shared connection would throttle everyone behind one NAT address — wrong for a gym-focused product. Same fixed-window mechanics, one dimension (per user). Recorded because the obvious reviewer question is "why not reuse it".
- (HEADER IS OPTIONAL, Kd-agreed) Mandating it would break the client shipped by web Card 4, which sends none. Keyless requests behave exactly as before and are protected by the cap alone — pinned by a test asserting two identical keyless sends still produce two threads.

## Deploy infrastructure — Dockerfile + compose + where the worker runs (2026-07-24; branch `deploy-infra`)

- (THE PLAN AMENDMENT THAT VERIFICATION FORCED — R1.2, declared not slipped in) The approved plan said "a named volume for the HuggingFace model cache". **That would have mounted over nothing.** transformers.js v4.2.0 reads NO `process.env` at all (`src/env.js`: `DEFAULT_CACHE_DIR = path.join(dirname__, '/.cache/')`), so `HF_HOME`/`TRANSFORMERS_CACHE` are inert and the cache resolves INSIDE the package's own `node_modules` directory. The weights are therefore BAKED IN at build time by one warm embed, which also asserts the returned dim is Part 4 §3.7's pinned 384 — a silently-failed warm would otherwise defer the ~90 MB download to the first user request. This matters because the coach embeds the USER'S QUESTION in-process on every request (`coach/routes.ts` wires `createMiniLmEmbedder()` as the default; `service.ts` calls `retrieve(sql, embedder, message)`), which the plan had wrongly described as ingest-only. Consequence: a fresh container answers coach questions with no route to HuggingFace, and a redeploy costs no re-download.
- (BASE IMAGE = glibc/bookworm, deliberately) Three runtime deps carry platform-specific native binaries: `@node-rs/argon2` (every login), plus `onnxruntime-node` and `sharp` via `@huggingface/transformers` (every coach question). `pnpm-lock.yaml` carries BOTH `linux-x64-gnu` and `linux-x64-musl` argon2 variants (verified — 15 linux entries), so musl would also resolve; glibc is the conservative default and the PROVE exercises a real login and a real coach answer through the container rather than asserting the natives loaded. NB this machine's `node_modules` holds only `@node-rs/argon2-win32-x64-msvc`, which is why `**/node_modules` is dockerignored — copying it in would shadow the linux install.
- (BUILD FINDING 1 — `chown -R` was silently DOUBLING the image) The first build produced **3.14 GB**. `RUN chown -R node:node /app` rewrites every file in a multi-GB tree into a fresh layer, so the tree was stored twice; it also cost **170 s**. Replaced with `COPY --chown` (ownership applied as the layers are written) and — the part that matters more — the warm embed now runs AFTER `USER node`, so the model cache is written by the uid that reads it at runtime. Warming as root and then dropping privileges is how a container passes its build and fails its first request. Measured result: **3.14 GB → 1.74 GB**.
- (BUILD FINDING 2 — MY FIRST FIX FOR IT WAS INERT, AND ONLY MEASURING CAUGHT THAT) `onnxruntime-node`'s postinstall downloads the CUDA nupkg and extracts `libonnxruntime_providers_cuda.so` (**316 MB** measured in-image; 513 MB of providers in total) plus TensorRT — none of which can ever load on the CPU-only CX32 v1 §19 targets. I added `ONNXRUNTIME_NODE_INSTALL=skip`, flag verified against the installed `script/install.js` rather than recalled (`..._CUDA` is deprecated there). **The rebuild still shipped the full 316 MB file.** The size drop I was about to attribute to the skip came ENTIRELY from finding 1. Cause, measured not guessed: pnpm caches a package's POSTINSTALL OUTPUT in the store, so with a warm `--mount=type=cache` store the postinstall never re-ran — build 2's log contains zero onnxruntime postinstall lines — and the ENV was never consulted. Fixed with `--no-side-effects-cache`. **And the property is now ASSERTED IN THE BUILD** (fail if any `libonnxruntime_providers_cuda.so` exists, fail if the CPU `libonnxruntime.so.1` does not), because a cache behaviour is not a guarantee and this exact skip was already defeated by one. Same lesson this file keeps recording: a fix is not verified until the artifact is measured, and "the number moved" is not proof that the thing you changed is what moved it.
