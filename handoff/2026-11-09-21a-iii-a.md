# Handoff · 2026-11-09 · Stage 5 item 21a-iii-a, a size limit on every list sent to the server (feature folder 1; branch `21a-iii-security-updates`)

Kd's decisions: `rulings/2026-11-09-21a-iii.md`.

- **Why:** GitHub's zod alert. Measured: on zod 3.25.76 a 1 MB body of 500,000 wrong items kept 166 MB and a 14 MB one 2.5 GB (the server has 1 GB); on zod 4.6.7 the same list kept 4 MB with a `.max()` and 263 MB without one. 351 `z.array(` lines have no `.max()` on the line. **Risky** (every request's input). No migration, no new package.
- **What:** `apps/api/src/listLimit.ts`, a `preValidation` hook after the rate-limit floor: more than 25,000 list items in a body or query string, nested lists included, is 413 `too_many_items` before any route reads it. A route raises it with `config.listItemsMost`; the two run routes take `RUN_MAX_POINTS * 5 + RUN_MAX_PAUSES * 3` (222,000). The next-biggest real lists are 20,000 (member-list marks, price-raise ticks).
- **Worst thing, first test:** a member's longest run refused. Twelve hours of points and 2,000 pauses pass the check on both run routes, one point more is refused (`listLimit.unit.test.ts`), and the same run is saved, 201, on local Postgres (`geo.runs.record.routes.test.ts`).
- **Breaks:** every route held to 25,000 (1 red), lists inside lists not counted (6 red), off by one (4 red); put back.
- **Cost:** the walk takes 6.8 ms on the longest run, 0.46 ms on 25,000 ids, 0.005 ms on a 20-food meal; a 500,000-item list is refused at its length, without a walk (tsx, 200 runs each, on mains power).
- **Packages:** undici 7.29.0 to 7.30.1 (jsdom, tests only), follow-redirects 1.16.1 to 1.16.2 (axios, web; the browser does not use it), react-is 19.3.0 to 19.3.1 came with them (26 days old). node-forge 1.4.1 (the phone's build tool, `@expo/cli`) is 14 days old from 2026-11-10 04:44 UTC; one of its alerts has no fix in any version. vitest's critical alerts are its `--ui` server, never run here.
- **Proof:** api tsc 0, eslint 0; `listLimit.unit.test.ts` 9 of 9; `geo.runs.record.routes.test.ts` 16 of 16 (the first run timed out on a cold start; 15 of 15 on master's code, then 16 of 16). GitHub's first run: 8,878 of 8,879, `posts.routes.test.ts` expected a 100,000-item photo flood to reach the route's own 400; it now meets the 413 first, and a 20,000 flood keeps the route's 400 tested (17 of 17).
